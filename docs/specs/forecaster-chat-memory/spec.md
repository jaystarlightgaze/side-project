# 예보관과 대화, 로그인하면 이어지는 기억

예보 카드를 받은 회사원이 그 예보를 바탕으로 예보관과 처신을 상담한다. 로그인한 사용자는 지난 예보와 대화가 저장되어, 다음 날 예보관이 "어제 예보는 어땠어요?"라고 먼저 묻고, 털어놓은 결과가 오늘 예보와 대화에 이어진다. `PRODUCT.md` 핵심 흐름의 "예보관과 대화"와 "다음에 열 때 털어놓으면 기억된다" 단계를 처음으로 채운다.

연결된 자료:
- [PRODUCT.md](../../../PRODUCT.md) — 서비스 전체 방향. 이 Spec은 그중 "30초 안에 끝나는 가벼움", "나쁜 예보도 대안과 다독임으로 끝낸다", "예보가 빗나갔다는 불만도 받아 준다(변명하거나 탓하지 않고 다독인 뒤 다음 예보에 반영)", "기상청 은유 유지", "재미로 보는 예보임을 밝힌다"를 따른다.
- [daily-forecast-card spec](../daily-forecast-card/spec.md) — 이미 배포된 예보 카드의 동작. 이 Spec은 그 동작을 깨지 않고 위에 얹는다.
- [ui-composition](../../decisions/ui-composition.md) — 대화창, 로그인 화면, 헤더의 component와 상태 표현은 이 계약을 따른다.

## 사용자에게 보이는 결과

1. 예보 카드가 나오면 카드 아래에 "예보관에게 묻기" 대화창이 열린다. 예보관은 오늘 받은 예보(등급, 문구, 특보, 운 지수)를 알고 답한다.
2. 오늘의 특보가 있거나 운 지수가 아주 낮거나(30 이하) 아주 높으면(80 이상), 대화창 위에 "오늘은 예보관과 얘기해 보세요" 같은 권유 한 줄이 보인다.
3. 로그인하지 않은 사용자도 대화할 수 있다. 다만 대화는 저장되지 않고, 새로고침하면 사라진다.
4. 헤더에서 이메일과 비밀번호로 가입하거나 로그인할 수 있다. 로그인하면 입력값과 그날의 예보, 대화가 계정에 저장되고, 다른 기기에서 로그인해도 오늘 받은 예보와 대화가 그대로 보인다.
5. 로그인한 사용자가 다음 날 예보를 받으면, 대화창이 예보관의 질문으로 시작한다. 예: "어제는 '회의 주의보'였는데, 실제로는 어떠셨어요?" 사용자가 답하면 예보관이 먼저 다독이고, 그 내용이 저장된다.
6. 털어놓은 결과가 있으면 다음 예보 카드에 "지난 기억" 한 줄(날짜와 털어놓은 내용 요약)이 보이고, 예보 문구와 예보관 대화도 그 일을 이어서 언급할 수 있다.

## 승인된 범위

- 예보 카드 아래 예보관 대화(로그인 여부와 관계없이)
- 이메일과 비밀번호로 하는 선택 로그인, 가입, 로그아웃
- 로그인한 사용자의 입력값, 예보, 대화 저장과 본인만 보기
- 지난 예보를 바탕으로 예보관이 먼저 묻기, 털어놓은 결과 저장
- 지난 기억을 오늘 예보 카드와 대화에 반영

## 수용 기준

배포 주소에서 실제 브라우저로 아래를 확인한다.

- AC1. 로그인하지 않은 상태에서 예보를 받으면 카드 아래에 대화창이 나온다. 질문을 보내면 10초 안에 예보관의 한국어 답이 화면에 나타나기 시작하고, 답을 기다리는 동안에는 보내기 버튼을 다시 누를 수 없다.
- AC2. 예보 맥락이 대화에 전달되는지 아래 고정 사례 3개로 확인한다. 각 사례를 한 번씩 물어 3개 모두 통과해야 한다. 모델 출력이라 매번 다르므로, 하나라도 실패하면 같은 사례를 한 번 더 물어 보고 두 번 연속 실패하면 미통과로 본다.
  - 회의 주의보가 나온 예보에서 "오늘 회의 어떻게 버티지?" → 답에 회의 관련 조언이 있다.
  - 과열 지수가 폭염주의보인 예보에서 "오늘 일 많이 해도 될까?" → 답에 쉬기, 속도 조절 같은 과열 관련 조언이 있다.
  - 특보에 "오후 3시 팀장님께 휴가 결재 받기"를 적은 예보에서 "언제 말 꺼내지?" → 답이 휴가 결재나 시간대를 언급한다.
- AC3. 오늘의 특보를 적었거나 운 지수가 30 이하 또는 80 이상이면 대화 권유 한 줄이 보이고, 셋 다 아니면 보이지 않는다.
- AC4. 로그인하지 않은 상태에서 새로고침하면 대화 내용이 사라지고, 첫 Spec의 동작(입력값 기억, 예보 카드)은 그대로다.
- AC5. 새 이메일로 가입하면 별도 확인 메일 없이 바로 로그인 상태가 되고, 헤더가 로그인 상태(로그아웃 버튼)로 바뀐다. 로그아웃하면 다시 로그인 전 상태로 돌아간다.
- AC6. 로그인한 상태에서 예보를 받고 대화한 뒤, 다른 브라우저(또는 시크릿 창)에서 같은 계정으로 로그인하면 "예보 보기"를 누르지 않아도 입력값이 채워져 있고, 오늘 마지막으로 받은 예보 카드와 그 대화가 다시 보인다.
- AC7. 로그인한 사용자에게 지난 날짜의 예보가 저장돼 있으면, 오늘 첫 예보를 받은 직후 대화창이 그 지난 예보의 날짜와 항목 등급 하나를 언급하는 예보관 질문으로 시작한다. 지난 예보가 없으면 이 질문은 나오지 않는다. 오늘 이미 그 질문에 답했다면, 같은 날 예보를 다시 받아도 같은 질문을 또 하지 않는다.
- AC8. AC7의 질문에 답한 뒤 다음 날 예보를 받으면, 카드에 "지난 기억" 한 줄이 그 답의 내용과 함께 나온다. 최근 7일 안에 답한 것이 여럿이면 가장 최근 것 하나만 보인다. 답하지 않았다면 이 줄은 나오지 않는다.
- AC9. 다른 계정으로 로그인하면 앞 계정의 입력값, 예보, 대화가 보이지 않는다.
- AC10. 대화 응답이 실패하면(모델 오류, 요청 수 제한 등) 대화창에 실패 안내와 다시 보내기 방법이 보이고, 예보 카드는 그대로 남는다.

AC7과 AC8의 "다음 날"은 실제로 하루를 기다리지 않고, 저장된 지난 예보의 날짜를 Supabase 대시보드(SQL Editor 또는 Table Editor)에서 하루 전으로 바꾼 상태로 확인해도 된다. 이를 위해 앱에 날짜를 바꾸는 기능을 따로 만들지는 않는다.

## 정해진 제약과 이유

- **로그인은 선택:** 로그인하지 않아도 예보와 대화를 쓸 수 있고, 로그인하면 기억이 생긴다. 처음 온 사람에게 가입을 요구하면 "매일 30초" 원칙이 깨지고, 이미 배포된 첫 기능의 흐름도 바뀌기 때문이다. (사용자 확인)
- **결과는 예보관이 먼저 묻는다:** 지난 예보가 있으면 예보관이 대화에서 먼저 결과를 묻고, 사용자는 문장으로 답한다. 따로 "맞음/빗나감" 버튼이나 기록 폼은 두지 않는다. 대화 안에서 묻는 쪽이 30초 원칙과 "불만도 받아 준다" 원칙에 맞기 때문이다. 대신 결과가 정해진 칸으로 남지 않아 적중률 같은 통계는 낼 수 없다. (사용자 확인)
- **먼저 묻는 질문은 고정 문장:** AC7의 첫 질문은 저장된 지난 예보의 날짜와 등급으로 앱이 만든다. 모델이 지어내지 않으므로 지난 예보와 어긋나지 않는다.
- **본인 데이터만:** 저장된 입력값, 예보, 대화는 그 계정 본인만 읽고 쓸 수 있다. (setup-supabase 기본 패턴)
- **로그인 방식:** 이메일과 비밀번호. 이메일 확인은 끈다. 강의 일정 안에서 가입 즉시 써 볼 수 있게 하기 위해서다.
- **모델:** 예보와 대화 모두 AI Gateway를 거쳐 `google/gemini-2.5-flash-lite`를 쓴다. 무료 등급에서 쓸 수 있는 가장 싼 가격대 모델이다. (첫 Spec과 같음, 사용자 확인)
- **예보관의 선:** 예보관은 재미로 보는 예보의 캐릭터다. 실제 예언이나 전문 상담(심리, 법률, 의료)인 척하지 않고, 대화창에도 "재미로 보는 예보입니다" 안내가 보인다. (PRODUCT.md 경계)
- **나쁜 예보와 불만:** 예보관은 지난 예보가 빗나갔다는 말에 변명하거나 사용자를 탓하지 않고, 먼저 다독인 뒤 다음 행동을 제안한다. (PRODUCT.md 경험 원칙)
- **첫 Spec 유지:** 로그인하지 않은 사용자의 경험(입력값 브라우저 기억, 예보 카드, 실패 상태)은 첫 Spec의 수용 기준을 그대로 만족한다.
- **언어:** 화면, 예보, 대화 모두 한국어다.

## 가정 (에이전트가 정한 기본값, 바꿔도 됨)

- 대화창은 예보 카드가 나온 뒤에만 보인다. 예보 없이 대화만 하는 화면은 없다.
- 예보와 대화에 반영하는 기억은 최근 7일 치다. (PRODUCT.md의 "얼마나 오래 반영할지"는 아직 모름 항목이다)
- "지난 예보"는 오늘 이전 날짜 중 가장 최근 날의 마지막 예보다. 같은 날 예보를 여러 번 받으면 모두 저장하되, 기억에는 그날의 마지막 예보를 쓴다.
- 로그인한 사용자의 입력값은 계정에 저장되고, 같은 브라우저의 로컬 기억보다 계정 값을 우선한다.
- 로그인 전에 받은 예보와 대화는 로그인해도 계정으로 옮기지 않는다.
- 대화 한 번에 보내는 질문 길이는 500자까지다.
- 헤더에는 로그인 전에는 "로그인" 링크, 로그인 후에는 "로그아웃" 버튼만 둔다. 프로필 설정 화면은 만들지 않는다.

## 범위 밖과 이유

- 구글 등 소셜 로그인: OAuth 설정이 필요해 이번 일정 밖이다.
- 대화만 따로 여는 화면, 지난 대화 목록 보기: 핵심 흐름에 필요하지 않다.
- 예보 적중률 통계: 결과를 대화 문장으로만 받기로 했기 때문이다.
- 캘린더 연동, 앱이 중요한 날을 먼저 알아채기: PRODUCT.md에서 아직 모름이다.
- 주변인 생일(이벤트 전선), 아침 알림: 이번 범위 밖이다.
- 스펙이 요구하지 않은 남용 방지, 요청 수 제한 같은 보안 하드닝: AGENTS.md 예산상 범위 밖이다.

## 미룬 결정

- **기억을 얼마나 오래 반영할지:** 지금은 7일 가정으로 둔다. 사용자가 일주일 넘게 써 보고 "오래전 일을 너무 많이 꺼낸다" 또는 "금방 잊는다"고 느끼면 다시 연다.
- **로그인 전 기록을 계정으로 옮길지:** 로그인한 사용자가 "어제 로그인 전에 받은 예보가 없다"고 느끼면 다시 연다.

## 남은 위험

- AC2처럼 예보관 답의 내용을 보는 기준은 모델 출력이라 매번 다르다. AGENTS.md의 검증 예산에 맞춰 자동 eval 대신 고정 사례 3개를 배포 주소에서 직접 확인한다. 실제로 써 보며 답이 예보 맥락을 자주 놓치면 그때 eval을 붙인다.
- 무료 등급은 모델별 요청 수 제한이 있어, 대화를 빠르게 여러 번 보내면 429가 날 수 있다. 이때는 AC10의 실패 안내로 보인다.
- 사내 네트워크의 SSL 검사 때문에 로컬에서 Supabase CLI나 GitHub clone이 막힐 수 있다. Supabase 테이블과 권한 설정은 대시보드 SQL Editor로 적용해야 할 수 있다.
- 공식 Supabase 스킬은 SSL 문제로 설치하지 못했다. 구현은 `AGENTS.md`의 안내대로 `https://supabase.com/llms.txt`와 프로젝트 로컬 `setup-supabase` 스킬을 따른다.

## Setup before implementation

- Supabase 프로젝트의 URL과 publishable(anon) 키: 로그인과 저장에 필요하다. `.env.local`과 Vercel Environment Variables 양쪽에 넣는다. 완료 조건: 앱 밖에서 그 URL의 `/auth/v1/health`에 키를 붙여 요청하면 정상 응답이 온다.
- Supabase 대시보드에서 이메일 로그인 켜기, 이메일 확인 끄기: AC5의 즉시 로그인에 필요하다. 완료 조건: 대시보드 Authentication 설정에서 Email 공급자가 켜져 있고 "Confirm email"이 꺼져 있다.
- Supabase의 Site URL과 Redirect URL에 배포 주소(`https://side-project-nine-pi.vercel.app`)와 로컬 주소를 등록: 로그인 후 돌아올 주소에 필요하다. 완료 조건: 대시보드 Authentication URL 설정에 두 주소가 보인다.
